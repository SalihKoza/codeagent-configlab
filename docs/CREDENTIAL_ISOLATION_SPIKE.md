# CodeAgent ConfigLab — Credential-Isolation Spike

Status: **infrastructure spike, 2026-09-25.** This is not a benchmark task and has no
research value. It tests one candidate topology for the blocker recorded in
`docs/HARNESS_READINESS_SPIKE.md` ("Credential file readable by the agent").

Environment: WSL2 Ubuntu, user `cclab`, Claude Code **2.1.263** (native ELF build),
sandbox-runtime (`srt`) 0.0.77, bubblewrap 0.11.1, persisted Claude.ai Pro login.
No API key and no other provider.

Evidence: `spike/credential-isolation/spike.sh`. The WSL-side artifacts are in
`~/cclab-credspike/artifacts/`: `prep-meta.txt`, `cap.log`, `nest.log`, `m1.jsonl`,
`m1.err`, `m1-debug.log`, `cleanup.log`.

Model calls: **1** (`m1`, `haiku`). It consumed no tokens: both API attempts returned
401 (see Test 4).

Labels used below:
- **[obs]** observed in this spike;
- **[inf]** inference from observations;
- **[doc]** text in the 2.1.263 binary (schema descriptions and error strings), not verified behaviorally.

## Goal

The trusted Claude CLI keeps the access it needs to the persisted Pro auth state.
Model-controlled tools (Bash and its subprocesses, Read, Grep, Glob, Edit, Write) must
not be able to read credential contents.

## Threat boundary

- **Protected:** `/home/cclab/.claude/.credentials.json`, and for testing a fake
  fixture with the same shape.
- **Trusted:** the `claude` CLI process itself. It runs inside the outer `srt` sandbox,
  which must allow it to read the credential file.
- **Untrusted:** everything the model controls:
  - Bash commands and their children (Python, Node, …);
  - the arguments of the built-in file tools, which run inside the CLI process.
- **Out of scope:** attacks on the CLI process itself (ptrace, core dumps), and the network egress of secrets. Egress is already limited by the outer allowlist, but that does not protect the transcript or model context.

## Candidate topology tested

```
outer srt (unchanged "narrow" ro/impl shape from the readiness spike)
  └─ claude -p  (trusted; reads ~/.claude/.credentials.json)
       ├─ inner layer 1: Claude Code's own Bash sandbox        (for Bash/subprocesses)
       └─ inner layer 2: permissions.deny rules                (for Read/Edit/Write/Grep/Glob)
```

Both inner layers come from one inline `--settings '<json>'`, generated by
`protect_json REAL FAKE`. It is passed together with `--setting-sources ""`, so no file
that the agent could edit holds it. Resolved value (`~/cclab-credspike/settings/protect.json`):

```json
{"permissions":{"deny":[
   "Read(//home/cclab/.claude/.credentials.json)","Edit(//home/cclab/.claude/.credentials.json)","Write(//home/cclab/.claude/.credentials.json)",
   "Read(//home/cclab/cclab-credspike/fake-home/.claude/.credentials.json)","Edit(//…fake…)","Write(//…fake…)",
   "Read(**/.credentials.json)","Edit(**/.credentials.json)","Write(**/.credentials.json)"]},
 "sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,"autoAllowBashIfSandboxed":false,
   "credentials":{"files":[{"path":"/home/cclab/.claude/.credentials.json","mode":"deny"},
                           {"path":"/home/cclab/cclab-credspike/fake-home/.claude/.credentials.json","mode":"deny"}]},
   "filesystem":{"denyRead":["/home/cclab/.claude/.credentials.json","/home/cclab/cclab-credspike/fake-home/.claude/.credentials.json"]}}}
```

The outer `srt` config is the readiness spike's `impl` shape with one change: the fake
fixture gets the same rights as the real file (fake-home readable; the fixture file
writable).

## Test fixture

- `~/cclab-credspike/fake-home/.claude/.credentials.json`, mode 600, owner `cclab`.
  - Content: `{"claudeAiOauth":{"accessToken":"CREDSPIKE-CANARY-<16 random hex>","note":"SYNTHETIC FIXTURE, not a credential"}}`.
  - Sibling `decoy.txt` is unprotected.
- **Why it tests the same rule as the real file:**
  - same basename;
  - same `.claude/` parent shape (both parents mode 755, owner `cclab`);
  - same owner and mode;
  - same filesystem (`dev 2096`);
  - same outer-srt treatment: readable, and writable as a file.
  - It is emitted by the same `protect_json` call, into the same four rule lists, and the basename glob rules cover both.
- [obs] Outer sandbox only (`nest.log`): `test -r fake` → `readable`. This reproduces the original accessibility problem on the fixture.
- The real file was never overwritten or shadowed.

Protected Bash execution could not be established without loosening the outer sandbox.
The only way to let the inner runtime listen would be something like outer
`allowAllUnixSockets`. That undoes a verified outer property. By the decision made
before this spike, that weakening was **not** tried.

## Real credential path policy equivalence

Verified without reading the credential contents:
- [obs] `protect.json` contains the real path in exactly the same four lists and rule shapes as the fake: `credentials.files` deny, `filesystem.denyRead`, `Read(//…)`, `Edit(//…)`. The glob rules cover both files.
- [obs] The CLI loaded all 9 deny rules. The 3 `Write(...)` rules are inert.
- [obs] Real-file metadata: mode/owner/mtime/inode unchanged from prep to cleanup (`mode=600 owner=cclab mtime=1790168475 devino=2096:4261`).
- The file was never cat-ed, read, grepped, hashed, sized, copied or opened by the spike.

Policy-string equivalence holds. But the policy's enforcement was never observed, not
even on the fake. Real-path protection is therefore **UNVERIFIED**.

## C0/C1/C2 equality

The design keeps credential protection a common environmental control:
- one `protect_json` output, byte-identical, is passed as `--settings` to C0, C1, C2 phase 1 and C2 phase 2;
- the outer `ro`/`impl` srt config and `--tools` differ only in C2 phase 1, which is the existing treatment.

Equality of the *design* is shown. Equality of *enforcement* is moot, because the inner
layer does not start in any configuration.

## Limitations

- **OS-enforced** (observed):
  - the outer srt (unchanged from earlier spikes);
  - the outer AF_UNIX block, which is exactly what prevents the inner sandbox.
- **Claude permission layer:** rules load, but none was exercised. `Write(path)` rules are inert.
- **Best-effort / unclear:**
  - `failIfUnavailable` did not stop the session at startup;
  - `sandbox status` did not report the init failure;
  - project settings files in the WC are watched.
- **Untested:** all of Tests 1–3 beyond sandbox startup, Test 4, and the bypass classes listed in Test 3.

## Final decision

`NO-GO — credential isolation candidate failed`

Reason: Claude Code 2.1.263's inner Bash sandbox cannot initialize inside the existing
outer srt sandbox: `EPERM … listen '/tmp/claude/srt-mux-2-0.sock'`, from the outer
AF_UNIX seccomp block. Making it start would require weakening the outer sandbox
(or the inner one), and that is excluded. Separately:
- the fail-closed behavior did not show at startup;
- headless Pro inference inside the outer sandbox currently fails with an expired OAuth access token.
